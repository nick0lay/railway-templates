# Supabase

Self-hosted [Supabase](https://github.com/supabase/supabase) on Railway: Postgres with an instant REST and GraphQL API, Auth, Storage, Realtime and the Studio dashboard. This template runs the official Supabase images behind one gateway. Every secret is generated at deploy time and the API keys are derived automatically, so there is nothing to generate by hand. You get one URL, a publishable key and a secret key, ready for `supabase-js`.

## Architecture

```
            Your app (supabase-js)            You (browser)
                     │ HTTPS + API key               │ HTTPS + Studio login
                     ▼                               ▼
┌──────────────────────────────────────────────────────────────────────┐
│ Railway project                                                      │
│                                                                      │
│  Supabase :8000 (public gateway, Caddy)                              │
│    /auth/v1  /rest/v1  /graphql/v1  /realtime/v1  /storage/v1  /pg   │
│    checks API keys, swaps sb_ keys for JWTs, Studio behind login     │
│      │          │           │            │            │         │    │
│      ▼ :9999    ▼ :3000     ▼ :4000      ▼ :5000      ▼ :8080   ▼ :3000
│    Auth       REST       Realtime     Storage       Meta     Studio  │
│   (GoTrue) (PostgREST)              (volume:files)         (volume)  │
│      │          │           │            │            │         │    │
│      └──────────┴───────────┴─────┬──────┴────────────┴─────────┘    │
│                                   ▼ :5432                            │
│                     Postgres 17 (Supabase image, volume)             │
│                     TCP proxy for psql, migrations, Supabase CLI     │
└──────────────────────────────────────────────────────────────────────┘
```

## Services

| Service | Source | Role |
|---------|--------|------|
| Supabase | `caddy:2.10.2-alpine` | API gateway (public). Routes to every service, checks API keys, translates the opaque `sb_` keys to JWTs, puts Studio behind a login. Holds the URL and keys you use in apps |
| Postgres | `supabase/postgres:17.6.1.136` | Database with Supabase's extensions and roles (private network, plus a TCP proxy). Data on a volume |
| Auth | `supabase/gotrue:v2.197.0` | Sign-up, login, sessions, password reset, OAuth (private) |
| REST | `postgrest/postgrest:v14.18` | REST and GraphQL API generated from your tables (private) |
| Realtime | `supabase/realtime:v2.148.3` | Database change streams, broadcast and presence over WebSockets (private) |
| Storage | `supabase/storage-api:v1.89.12` | File storage with access policies, files on a volume (private) |
| Meta | `supabase/postgres-meta:v0.100.0` | Database metadata API used by Studio (private) |
| Studio | `supabase/studio:2026.11.02-sha-a05e7ec` | Dashboard: table editor, SQL editor, auth users, storage browser (private, served through the gateway). Saved SQL snippets on a volume |

## What this template does differently

- **No key generation step.** Supabase's docker setup asks you to sign the anon and service_role JWTs yourself, and other templates send you to a separate website to do it. Here the JWT secret is generated by Railway, and the gateway, Studio and Storage derive the same keys from it when they start.
- **Opaque API keys.** You use `SUPABASE_PUBLISHABLE_KEY` (`sb_publishable_...`) in apps and `SUPABASE_SECRET_KEY` (`sb_secret_...`) on servers, like hosted Supabase. The gateway swaps them for the matching JWT, so the services behind it only see JWTs. The legacy anon and service_role JWT keys also work.
- **Locked down by default.** Studio needs the dashboard login. REST, GraphQL, Auth, Realtime and the metadata API need an API key; the metadata API (`/pg`) and the REST schema description need the secret key. Auth's admin API needs the secret key. Postgres is reachable from outside only with its generated password.
- **Database set up on first start.** Postgres runs Supabase's own first-start SQL from the docker setup (role passwords, Realtime schema, database webhooks, JWT settings, internal `_supabase` database). The Vault and pgsodium root key is kept in a variable, so encrypted secrets survive redeploys.
- **No startup race.** Auth, Storage and Realtime wait until Postgres accepts connections before starting, so the first deploy comes up without manual redeploys.
- **Pinned versions** of every image, as in Supabase's docker-compose file of 2026-11-02.

## After deploy

The first deploy takes 2 to 4 minutes.

1. Open the `Supabase` service → **Variables**. You need `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY`.
2. Open `SUPABASE_URL` in a browser and log in to Studio with `DASHBOARD_USERNAME` and `DASHBOARD_PASSWORD` (same service).
3. Create tables in the Table Editor or SQL Editor. Turn on Row Level Security and add policies before you use the publishable key from a browser.
4. Connect your app:

   ```js
   import { createClient } from '@supabase/supabase-js'
   const supabase = createClient(SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY)
   ```

5. Set `SITE_URL` (and `ADDITIONAL_REDIRECT_URLS`) on the `Auth` service to your app's URL, so email links and OAuth redirect there.
6. For production email (confirmations, magic links, password resets), fill in the `GOTRUE_SMTP_*` variables on `Auth` and set `GOTRUE_MAILER_AUTOCONFIRM` to `false`.

To connect to Postgres directly (psql, migrations, Prisma, `supabase db push`), use `DATABASE_PUBLIC_URL` from the `Postgres` service. Inside the project, use `DATABASE_URL`.

## Variables

### User-configurable

| Service | Variable | Default | Notes |
|---|---|---|---|
| Supabase | `DASHBOARD_USERNAME`, `DASHBOARD_PASSWORD` | `supabase`, generated | Studio login |
| Supabase | `SUPABASE_PUBLISHABLE_KEY` | generated `sb_publishable_...` | For browsers and apps; Row Level Security applies |
| Supabase | `SUPABASE_SECRET_KEY` | generated `sb_secret_...` | For servers only; bypasses Row Level Security |
| Supabase | `JWT_SECRET` | generated | Signs sessions and the legacy keys. Changing it logs everyone out and changes the legacy keys |
| Auth | `SITE_URL`, `ADDITIONAL_REDIRECT_URLS` | `http://localhost:3000`, empty | Where email links and OAuth send users |
| Auth | `GOTRUE_DISABLE_SIGNUP` | `false` | `true` closes public sign-up; invite or create users in Studio |
| Auth | `GOTRUE_MAILER_AUTOCONFIRM` | `true` | Confirms email users without an email. Set `false` once SMTP works |
| Auth | `GOTRUE_SMTP_HOST`, `_PORT`, `_USER`, `_PASS`, `_ADMIN_EMAIL`, `_SENDER_NAME` | empty / `587` / `admin@example.com` / `Supabase` | SMTP for auth emails |
| Auth | `GOTRUE_EXTERNAL_ANONYMOUS_USERS_ENABLED`, `GOTRUE_EXTERNAL_PHONE_ENABLED` | `false` | Anonymous and phone sign-in. OAuth providers use the `GOTRUE_EXTERNAL_<PROVIDER>_*` variables from the [Auth docs](https://github.com/supabase/auth) |
| Auth | `GOTRUE_JWT_EXP` | `3600` | Session token lifetime in seconds |
| REST | `PGRST_DB_SCHEMAS` | `public,storage,graphql_public` | Schemas exposed by the API |
| Storage | `FILE_SIZE_LIMIT` | `52428800` | Largest upload in bytes |
| Studio | `OPENAI_API_KEY` | empty | Enables the AI assistant in Studio |

### Auto-configured (do not change)

| Service | Variable | Why |
|---|---|---|
| Postgres | `POSTGRES_PASSWORD` | Password of `postgres`, `supabase_admin` and Supabase's internal roles, set on first start. Every service connects with it |
| Postgres | `PGSODIUM_ROOT_KEY` | Vault encryption key. Changing or losing it makes encrypted secrets unreadable |
| Postgres | `POSTGRES_INIT_SH` | Start script: writes Supabase's first-start SQL, then starts Postgres |
| Supabase | `*_UPSTREAM`, `CADDYFILE`, `JWT_KEYS_SH`, `GATEWAY_RUN_SH` | Private addresses of the services, gateway routes, key derivation and start script |
| Auth, REST, Realtime, Storage, Studio | `*JWT_SECRET` | `${{Supabase.JWT_SECRET}}` |
| Auth, REST, Realtime, Storage, Meta, Studio | database URLs and hosts | `${{Postgres.RAILWAY_PRIVATE_DOMAIN}}` and `${{Postgres.POSTGRES_PASSWORD}}`, each with its own Supabase role |
| Realtime | `DB_ENC_KEY`, `SECRET_KEY_BASE` | Generated encryption and session keys |
| Storage | `S3_PROTOCOL_ACCESS_KEY_ID`, `S3_PROTOCOL_ACCESS_KEY_SECRET` | Generated credentials for Storage's S3-compatible endpoint |
| Studio, Meta | `PG_META_CRYPTO_KEY` / `CRYPTO_KEY` | Shared encryption key between Studio and Meta |
| All | `*_RUN_SH` | Start scripts run by the start command |

## Not included

- **Edge Functions.** Run functions elsewhere (for example a Railway service with Deno) and call Supabase from them.
- **Log explorer** (Logflare and Vector). Use each service's logs in Railway.
- **Image transformations** (imgproxy). Storage serves original files.
- **Supavisor connection pooler.** Connect to Postgres directly; it allows 100 connections by default.
- **GraphQL** is routed, but the `pg_graphql` extension is off by default in current Supabase images. Turn it on with `create extension pg_graphql;` in the SQL Editor.

## Custom domain

Add the domain to the `Supabase` service. `SUPABASE_URL`, the Auth URLs and Storage URLs follow `RAILWAY_PUBLIC_DOMAIN`, so redeploy all services after adding it.

## Upgrading

Supabase publishes tested image versions in its [docker-compose file](https://github.com/supabase/supabase/blob/master/docker/docker-compose.yml) and [changelog](https://github.com/supabase/supabase/blob/master/docker/CHANGELOG.md). Change the image tags of the services to the versions listed there and redeploy. Back up Postgres first (`pg_dump` over `DATABASE_PUBLIC_URL`, or a volume snapshot). Major Postgres upgrades need Supabase's upgrade steps.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `{"message":"Invalid API key"}` (401) | Send the key in the `apikey` header (supabase-js does this). Use the keys from the `Supabase` service |
| Studio asks for a login again and again | Use `DASHBOARD_USERNAME` and `DASHBOARD_PASSWORD` from the `Supabase` service |
| Sign-up returns an error about sending email | SMTP is set but not working, or `GOTRUE_MAILER_AUTOCONFIRM` is `false` without SMTP |
| Email links point to `localhost:3000` | Set `SITE_URL` on the `Auth` service |
| A service fails after you changed `POSTGRES_PASSWORD` | The database roles keep the password from the first start. Set the variable back, or change the role passwords in SQL first |
| `pg_graphql extension is not enabled` | Run `create extension pg_graphql;` in the SQL Editor |

## Testing

Tested on 2026-11-07 in a throwaway Railway project, deployed from the template: all eight services were healthy about a minute after the first deploy, with no manual redeploys. Studio refused requests without a login or with a wrong password (401) and loaded with the generated one; its table list and SQL editor reached Postgres. REST and Auth refused requests without an API key or with a wrong one (401). Auth's admin API and the metadata API refused the publishable key (403) and accepted the secret key. Tables with Row Level Security were created over the metadata API. Two users signed up and signed in with the publishable key; each saw only their own rows, the publishable key alone saw none and couldn't insert, and the secret key saw all rows. A wrong password was refused (400). A private bucket was created with the secret key (refused with the publishable key), a file was uploaded and downloaded intact, and a signed URL worked; downloads without a key or with the publishable key were refused. Realtime refused a connection without a key; with the publishable key a channel received its own broadcast and a database insert as a change event. A Vault secret was stored and read back. Postgres accepted the generated password over the TCP proxy and refused a wrong one. The legacy anon and service_role JWTs derived from `JWT_SECRET` also worked. After redeploying all eight services, users, rows, files and the Vault secret were still there, and every check passed again. Email sending, OAuth providers and the Supabase CLI weren't tested.
